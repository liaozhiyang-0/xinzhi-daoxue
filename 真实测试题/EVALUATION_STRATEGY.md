# 六门课程智能体评估指标与可视化策略

## 1. 本轮范围

本轮只固定评估口径、输出结构和可视化方案，不执行 336 题全量测试，
不产生或声明任何真实模型准确率、耗时、Token 或费用结果。

正式评测对象为 `统一格式/balanced_336/all_cases.json`，共 336 题，
六门课各 56 题：

| 评测群组 | 数量 | 用途 |
|---|---:|---|
| 有参考答案题 | 157 | 其中145道评价普通答案，12道评价查错能力 |
| 普通答案题 | 145 | 使用参考答案评价学科解答 |
| 查错专项子集 | 12 | 评价能否识别学生首个错误、错误类型和核验状态 |
| 边界题 | 12 | 评价条件不足、矛盾、非法输入等情况下的合规处理 |
| 无答案题 | 167 | 只评价执行、路由、稳定性、耗时和资源消耗 |

12 道查错题属于 157 道有参考答案题，不能再次相加，也不能因教学策略
不披露完整答案而按普通解题判错。12 道边界题使用行为期望评分，不计入
普通学科答案正确率。

## 2. 首要原则

1. **任务完成不等于答案正确。** `completed`、HTTP 200 或 Provider 返回
   内容只能说明执行完成。
2. **无答案题正确率为 N/A。** 167 道无答案题不能当作错误，也不能进入
   学科答案正确率分母。
3. **失败、错误和超时分开。** `failed` 表示已完成但质量不达标；
   `error` 表示执行异常；`timeout` 单独统计。
4. **正确率同时给严格值和条件值。** 严格正确率将缺失结果、执行错误和
   超时视为未通过；条件正确率只看已有实质判分的答案。
5. **每个比例显示分子、分母和 95% Wilson 置信区间。** 小样本查错与
   边界题不能只显示一个百分比。
6. **Token 缺失必须显式暴露。** Provider 未返回 usage 时，不用 0
   代替，显示覆盖率和“部分统计”。
7. **不猜费用。** 只有确认模型与版本对应的价格表后才计算成本。

## 3. 答案正确率的判分前提

当前仓库默认规则评分器主要检查任务状态、显式关键词、步骤和数值约束。
多数真实参考答案题只有 `reference_answer`，没有足够的显式规则；因此默认
`answer_passed` 不能直接当作学科正确率。

全量测试前，145 道普通答案题必须产生独立的
`actual.answer_evaluation`：

```json
{
  "passed": true,
  "score": 0.92,
  "judge": "hybrid",
  "reference_used": true,
  "reason": "最终数值、关键推导和单位与参考答案一致"
}
```

允许的实质判分方式：

- 已复核答案按答案文本 SHA-256 精确绑定复用；同题答案内容变化后旧判定
  自动失效；
- 可确定数值题：公式/数值/单位规则优先；
- 开放推导题：使用三行简易协议
  `VERDICT/SCORE/REASON` 做参考答案约束下的语义判分；
- 无法稳定自动判断：转人工复核；
- 已声明 `required_keywords`、`required_equations`、`required_steps` 或
  `numeric_expectations` 的题，可使用显式规则评分。

若没有上述判分证据，汇总工具把普通答案正确率显示为 N/A。查错题另外核验
`verification_report_valid`、预期核验状态、错误类型和首个确认错误；边界题
核验行为期望、安全和禁止断言。

超时、执行错误或空答案在严格正确率中按未通过计入分母，但不生成伪造的
答案判定，因此从条件正确率分母和答案判分覆盖率分子中排除。

建议在首轮全量测试后，从“自动判对”和“自动判错”中各分层抽取至少 10%
人工复核，报告自动判分与人工结论的一致率。该一致率未建立前，所有答案
正确率均标记为“非官方评测”。

模型判分不再要求严格 JSON。JSON 字段或枚举格式错误属于评测基础设施失败，
不应覆盖智能体原始结果。简易协议无法解析时保留为 `judge unavailable`，
并降低判分覆盖率；原题执行、答案、耗时和 Token 仍正常保存。

## 4. 核心指标

### 4.1 数据完整性

| 指标 | 计算 |
|---|---|
| 结果覆盖率 | 唯一结果数 / 本次选中题数 |
| 答案判分覆盖率 | 有实质答案判分的题数 / 本次有答案题数 |
| Token 调用覆盖率 | 返回 `total_tokens` 的模型调用数 / 模型调用总数 |
| 题级 Token 覆盖率 | 所有调用均有 Token 的题数 / 有结果题数 |

结果覆盖率不是性能分，但它决定其他指标是否可信。

### 4.2 正确性与能力

| 指标 | 严格分母 |
|---|---|
| 普通答案严格正确率 | 本次选中的普通答案题，预期 145 |
| 普通答案条件正确率 | 已取得实质答案判分的有答案题 |
| 查错准确率 | 本次选中的查错题，预期 12 |
| 边界合规率 | 本次选中的边界题，预期 12 |
| 总体评测通过率 | 本次全部选中题；只反映完整合同通过 |
| 路由/课程/Agent 准确率 | 对应字段有评分结果的题 |

六科同时报告微平均和宏平均。微平均按题数汇总；宏平均为六科指标简单平均，
避免题量或判分覆盖差异掩盖弱科。

### 4.3 稳定性与失败

| 指标 | 说明 |
|---|---|
| 执行成功率 | 到达可评分终态的题数 / 选中题数 |
| 质量失败数 | 执行完成但合同或答案不达标 |
| 执行错误数 | 请求、运行时或 Provider 异常 |
| 超时数/超时率 | 单独统计，不并入普通错误 |
| 缺失结果数 | 选中题数减去唯一结果数 |
| 回退率 | 使用 fallback 的题数 / 有结果题数 |
| 重试次数 | 所有模型调用的重试次数总和 |
| 失败阶段与错误类型 | 按 `failure_stage`、`error_types` 聚合 |

### 4.4 时间效率

以每题端到端 `elapsed_ms` 为主，包含会话、上传、路由、RAG、Provider 和
结果整理；报告平均值、最小值、最大值及 P50/P90/P95/P99。按课程、输入类型、
题组和结果状态拆分。下一步若执行链提供阶段耗时，再增加：

- 排队耗时；
- 文件上传/预处理耗时；
- RAG 耗时；
- Provider 耗时；
- 后处理与评分耗时。

阶段字段缺失时不从端到端耗时反推。

### 4.5 Token 与模型资源

报告输入、输出和总 Token，至少包含：

- 已知 Token 总量；
- 每题 Token 的平均值、P50/P90/P95/P99 和最大值；
- 每个正确答案消耗的 Token；
- 质量失败、执行错误和超时所消耗的已知 Token 及占比；
- 每题模型调用数、回退率、重试次数；
- 按课程、题组和模型分组。

“每个正确答案 Token”是总投入除以实质判对题数，用于衡量有效产出；不能
只统计成功题的 Token 而隐藏失败消耗。

## 5. 初始阈值

`evaluation_metrics.json` 中的阈值是首轮预警线，不是已验证 SLA：

| 指标 | 初始预警目标 |
|---|---:|
| 结果覆盖率 | 100% |
| 普通答案严格正确率 | ≥ 80% |
| 普通答案条件正确率 | ≥ 85% |
| 查错准确率 | ≥ 80% |
| 边界合规率 | ≥ 90% |
| 执行成功率 | ≥ 95% |
| 路由准确率 | ≥ 98% |
| 超时率 | ≤ 3% |
| P95 端到端耗时 | ≤ 180 秒 |
| Token 调用覆盖率 | ≥ 95% |

Token 预算和成本阈值必须在首次完整测量后按实际分布校准，当前不设虚构目标。
阈值调整要保留版本和理由，不能通过删题或改变分母提高结果。

## 6. 可视化策略

主面板使用固定结构：

1. **总览卡片**：覆盖率、严格正确率、执行成功率、失败/超时数、
   P50/P95、已知 Token 和 Token 覆盖率。
2. **六科对比柱状图**：严格正确率、执行成功率、路由准确率，柱上显示
   样本数和置信区间。
3. **课程-指标热力图**：快速定位弱科和系统性短板。
4. **执行漏斗**：选中 → 有结果 → 执行完成 → 路由通过 → 结构通过 →
   答案通过 → 完整评测通过。
5. **耗时箱线图**：按课程展示分布，并标注 P50、P95 和超时线。
6. **Token 箱线图**：只使用题级 Token 完整的样本；标题显示覆盖率。
7. **Token-耗时散点图**：颜色表示状态，分面表示课程，用于找高耗低效题。
8. **失败帕累托图**：失败阶段和错误类型按频次排序并显示累计占比。
9. **查错与边界专项图**：按课程展示 12+12 小样本结果和置信区间。
10. **观测完整性面板**：结果、答案判分和 Token 覆盖率，避免误读。

不使用雷达图，因为六科和多指标比较容易被面积误导。绿色只表示通过，黄色
表示预警，红色表示失败，灰色表示 N/A；课程颜色固定，详见
`visualization_strategy.json`。

## 7. 产物与使用方式

全量测试产生 EvaluationRunner JSON 后，在仓库根目录运行：

```powershell
.\.venv\Scripts\python.exe .\真实测试题\analyze_evaluation_report.py `
  --results .\真实测试题\统一格式\reports\<evaluation-report>.json
```

脚本只读原始报告，不调用模型或 API，并输出：

```text
真实测试题/统一格式/evaluation_reports/
├── metrics_summary.json
├── case_metrics.csv
└── visualization_data.json
```

如果输入的是 `run_api_tests.py` 的原始任务报告，执行成功率和耗时仍可统计，
但因为缺少实质判分和逐调用 Token，正确率和 Token 指标会显示 N/A。正式全量
评测应使用带 `EvaluationResult.model_calls` 和 `actual.answer_evaluation`
的报告。

本轮口径验证命令：

```powershell
.\.venv\Scripts\python.exe .\真实测试题\validate_evaluation_metrics.py
```

它只核验 336 题分组合同并在临时目录用 5 条合成结果校验公式，不运行真实题，
不启动 Provider，也不产生模型费用。
