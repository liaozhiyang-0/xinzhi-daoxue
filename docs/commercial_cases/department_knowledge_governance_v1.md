# 案例五：学院知识库治理与课程资产发布

`scenario_id`: `department_knowledge_governance_v1`  
当前完成度：**内容和治理闭环已完成；当前运行时在未配置正式知识问答 Agent 时会降级到 `LEARN_01_LOCAL_RETRIEVAL_V1`，生产发布和学院试点待补。**

## 1. 定位

一句话：为学院建立课程资产的版本、来源、质量、审批和访问控制台，让“能检索”与“可发布”分开。

真实问题是课程资料多版本、来源不清、重复上传、审核状态不可见，直接接入 RAG 会把未审资料当答案。用户是学院管理员、教务和课程负责人，付费客户是学院/教务处或教育数字化服务商；场景是入库审查、版本发布、检索引用和权限审计。市场规模、项目报价和运维成本**待补证据**。

## 2. 产品与技术

- 产品：资产治理空间；提交课程资料后生成资产清单、版本/来源缺口、质量问题、审查队列、发布审批和检索验证。
- 架构：资料提交 → 资产/来源/版本校验 → 人工审查 → 发布索引 → `LEARN_01_KNOWLEDGE_QA_V1`；未配置时声明降级 `LEARN_01_LOCAL_RETRIEVAL_V1`，不把它描述成正式治理 Agent。
- 难点：版本一致性、版权/授权、来源证据、权限隔离、发布回滚、检索结果与发布状态绑定。
- 可行性：场景证据策略声明 `knowledge_manifest`、`asset_review_queue`、`published_course_asset`；前端证据卡片、审查状态和场景 review API 已存在。
- MVP：CT 课程资产清单+人工发布；试点版：多课程/权限/回滚；规模化：校级空间、审计和服务商交付。正式知识治理 Agent 发布记录待补。

## 3. 商业模式

学院/教务处或教育数字化服务商付费，按学院空间、课程资产量和治理服务订阅；价格、资产量和续费率**待补证据**。获客通过学院资料治理项目，交付包括盘点、规则、审批流、索引和培训。复购来自新学期资产、课程群、权限审计和校级扩展。成本是资产整理、索引、权限实施、存储、人工审核和运维。单位经济：`空间/服务收入 - 资产治理人时 - 索引/存储 - 运维`。三年路径：单学院→多学院→校级知识服务/服务商生态。

## 4. 市场与竞争

边界是“课程资产治理与可控发布”，不是万能知识库，也不自动发布未经审批内容。工程需求来自 `config/scenarios.yaml`、`docs/implementation/p61_contest_scenario_catalog.md`、场景证据审查 API 和资产/索引相关代码；外部市场/竞品/政策**待补证据**。

| 替代 | 局限 | 差异 |
| --- | --- | --- |
| 网盘/文件夹 | 版本和审批弱 | 资产、来源、发布状态结构化 |
| 直接建 RAG | 未审内容可被召回 | 先审查、再发布、可回滚 |
| 人工台账 | 维护成本高 | 任务、证据、索引和审计同链路 |

壁垒是校内资产授权和版本历史、审批/权限流程、发布索引与审计；复制 UI 容易，复制学校治理流程和数据授权难。当前不是已验证壁垒，需客户试点证明。

## 5. 落地计划

0—3个月：CT 单学院盘点、质量队列、审批和发布前检索验证；3—12个月：多课程授权试点，记录入库周期、引用完整率和回滚次数，基线待补；12—36个月：校级空间、服务商接口、权限和审计。团队：知识治理/教务、数据工程、Agent/RAG、前端、合规和实施。风险：版权、教师资料隐私、访问越权、错误发布、历史版本污染；默认最小权限、人工审批、版本锁和拒绝跨空间检索。

## 6. 路演表达

**30秒**：学院真正缺的不是更多文件，而是知道哪些资料能发布、版本是什么、来源在哪里、谁批准过。我们的知识库治理台把资产盘点、审查、发布和检索验证串起来；在正式 Agent 未发布时安全降级，不把降级结果冒充生产问答。

**3分钟**：直接把资料接入知识库会放大版本和版权问题。系统先做资产清单、来源和质量检查，进入人工队列；审批后发布索引，检索结果带版本和引用，支持回滚。付费者是学院/教务或数字化服务商，按空间和资产治理交付。先做单学院，再扩展校级。

**5分钟要点**：发布是治理动作不是模型动作；场景证据策略限制来源；权限和审批是核心；当前 preflight 已明确本地 fallback 与 production 阻塞；真实学院数据、成本和采购证据待补。

**10问10答**：1.谁付费=学院/教务/服务商；2.和网盘区别=版本/来源/审批/检索；3.为什么不自动发布=责任与版权；4.如何防串库=空间/角色/任务隔离；5.当前能生产吗=正式 Agent 未配置，安全降级演示；6.准确率=需发布资产评测；7.价格=按空间/资产待验证；8.回滚=版本和索引绑定；9.版权=授权与审查；10.扩展=校级治理，不改 Solver。

画布：学院/服务商付费；价值=可发布、可追溯、可回滚；渠道=资产治理项目；收入=空间/资产/服务；成本=清洗、索引、存储、审核、运维；伙伴=教务/LMS。技术一页：上传→manifest/quality→人工 review→发布索引→有版本引用的问答→审计。路线：单院→多院→校级。财务：`服务收入-治理/索引/运维成本`，无虚构数值。

## 7. 六个演示案例

| 编号 | 目标与输入 | 操作/路由/知识 | 输出价值 | 失败备用 |
| --- | --- | --- | --- | --- |
| D1 | 提交一份 CT 课程资料 | 选择场景、提交脱敏文本；治理 Agent/本地 fallback | 资产清单、版本与缺口 | 无正式 Agent 则标 fallback_only |
| D2 | 缺来源/授权信息 | 输入无 provenance 资料 | 审查问题与阻塞原因 | 只显示待补证据，不发布 |
| D3 | 两个版本冲突 | 提交 v1/v2 摘要 | 版本比较与推荐待审版本 | 无 checksum 时人工判定 |
| D4 | 审批发布 | 通过 review API 提交来源元数据 | approved/needs_manual_review/rejected 状态 | 不满足来源要求则拒绝 |
| D5 | 发布后检索 | 用已发布主题查询 | 引用版本与来源卡片 | 未发布资料不得召回 |
| D6 | 权限与回滚 | 要求学生访问草稿或恢复旧版 | 拒绝越权/展示回滚流程 | API 演示审计事件 |
