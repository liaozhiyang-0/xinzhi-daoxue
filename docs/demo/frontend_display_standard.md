# 六案例前端展示规范

## 1. 展示原则

前端只展示用户可理解、可复核的执行信息：

- 展示任务阶段、能力类别、证据和复核状态；
- 不展示模型私有推理链；
- 不把内部 ID、原始事件类型或调试字段作为主要内容；
- 结论、证据不足和人工复核都必须有明确视觉区分；
- 所有案例使用同一套布局和结果顺序。

## 2. 三栏工作区

### 左栏：案例选择

显示六张案例卡，每张卡包含：

- 中文案例名称；
- 简短业务描述；
- 能力标签；
- 案例编号；
- 示例输入或示例附件状态。

业务 ID 可以用于内部契约和测试，但不应替代中文案例名称成为用户主标题。

### 中栏：任务输入与结果

结果按以下顺序展示：

1. 摘要；
2. 核心结论；
3. 分析与计划；
4. 证据与依据；
5. 复核与限制；
6. 下一步。

输入区支持文本和材料附件。案例 6 的图片作为普通 `File` 进入已有上传接口，不绕过任务创建和材料摄取流程。

### 右栏：执行轨迹

统一使用六个阶段：

```text
任务理解 → 任务规划 → 能力调用 → 证据准备 → 结果复核 → 结果提交
```

每个阶段只显示用户需要知道的状态：等待、执行中、已完成、需复核或失败。任务进入 `waiting_review` / `waiting_user` 时，右栏和结果区必须同时提示人工边界。

## 3. 结果状态规范

| 状态 | 用户看到的文案 | 处理原则 |
| --- | --- | --- |
| queued/running | 任务正在执行 | 显示轨迹和轮询状态，不提前展示最终结论 |
| waiting_review | 等待人工复核 | 显示已到达复核门，不伪装成完成 |
| waiting_user | 等待补充信息 | 明确需要用户补充的字段 |
| completed | 已完成 | 展示结构化结果、证据和限制 |
| partial/insufficient | 需要复核 | 允许展示已有信息，但必须显示证据不足和风险 |
| failed | 执行失败 | 说明可操作的失败原因和重试建议 |

## 4. 六案例展示差异

| 案例 | 轨迹中应突出 | 结果区应突出 |
| --- | --- | --- |
| TP-01 | 计划、课程资料、教学技能 | 课堂可执行性、教师确认点 |
| FE-01 | 验证、首错定位、反馈生成 | 错误传播和验证任务 |
| LP-01 | 学习状态、前置关系、计划 | 优先级、阶段目标、复测条件 |
| RB-01 | 检索、证据治理、引用核验 | 来源、冲突、未核实结论 |
| KG-01 | 版本、权限、发布审批 | 发布决策、风险、回滚边界 |
| AC-01 | 图像理解、求解、工具、复核 | 拓扑证据、参数假设、饱和边界 |

## 5. 公式与长内容

- Markdown 内容统一经过 `MarkdownRenderer`；
- 行内公式和块级公式使用 KaTeX；
- 长公式允许横向滚动，不压缩到不可读；
- 公式显示失败时保留原始源码，并提示“公式暂时无法完整显示”；
- 公式和结构化字段都应支持复制或查看原文；
- 代码、表格和证据文本不得被公式预处理器误改写。

## 6. 禁止事项

- 不把原始 JSON 直接作为主结果；
- 不把内部任务 ID、Agent ID、事件名作为用户标题；
- 不把“模型没有证据”渲染成确定结论；
- 不在前端绕过现有 Task API 直接调用 Provider；
- 不通过启用隐藏场景或新增 Agent 来修复单个演示案例。
