# 学科智能体项目功能与架构审计报告

**审计日期：** 2026-08-21
**审计范围：** 六个展示案例、真实模型调用、Runtime、RAG、发布就绪度、工作台前端和基础 Agent 架构
**审计原则：** 只记录已观察到的事实；Mock、契约测试和真实模型结果严格区分；本报告不代表发布批准。
**本轮变更：** 仅新增本报告，未修改业务代码、配置或数据库。

---

## 1. 执行摘要

项目已经具备 Agent 平台的基础骨架，包括 Agent 注册表、路由器、结构化输出、durable Runtime、工具注册、SSE 和基础观测能力。

但当前系统还不能视为稳定的生产级智能体平台。实际状态更接近：

> 具备 Agent Runtime 雏形的学科任务编排平台。

主要原因如下：

1. 工作台后台当前实际使用 Mock，真实 Qwen 健康状态没有接入实际任务链路。
2. 备课等复杂结构化任务存在输出截断，失败信息无法直接定位根因。
3. RAG 处于 degraded，embedding 和 reranker 未加载，课程资料核验能力不稳定。
4. Runtime 与 Legacy 执行分支并存，尚未形成单一执行控制面。
5. 知识治理案例复用了学习路径 Agent，存在能力错配。
6. 真实发布证据不足，主要案例只能判定为演示可用，不能判定为生产可用。

## 3. 六个展示案例审计

### 3.1 教师备课

**入口：** `TEACH_01_LESSON_PREP_V1`
**路由：** 正确
**真实模型状态：** 不稳定
**RAG 依赖：** 是
**发布状态：** 未达到生产发布条件

真实 Qwen 测试显示：

- 在 1200 tokens 下，模型输出达到上限并触发 `StructuredOutputError`；
- 提高到 2400 tokens 后，模型以 `finish_reason=stop` 返回合法 JSON；
- 说明模型具备完成任务的能力，但输出预算和结构化恢复策略不足。

**结论：** 路由和业务契约存在，但复杂备课任务还不能稳定执行。

### 3.2 作业诊断

**入口：** `TEACH_02_ASSIGNMENT_REVIEW_V1`
**路由：** 正确
**真实模型状态：** 在较高预算下可返回合法结构
**发布状态：** 未达到生产发布条件

作业诊断在 1200 tokens 下返回了结构化结果，包括首错、错误传播、提示和验证任务字段。

但仍缺少：

- 连续真实样本的一致性证据；
- 标准答案、评分规则和人工复核数据；
- 发布版本与 Runtime Plan 版本的配对证据。

**结论：** 比备课稳定，但当前仍属于真实调用可行，尚非生产发布完成。

### 3.3 学生学习路径

**入口：** `LEARN_01_LOCAL_RETRIEVAL_V1`
**路由：** 正确
**主要风险：** 证据不足和启发式判断

当前配置显示学习环路为：

- `uncalibrated_heuristic`；
- 主动调度未启用；
- 反馈吸收模型未启用。

系统可以依据输入生成学习建议，但还不能把一次或少量作答稳定地转化为可靠能力判断。

**结论：** 可生成建议，不应宣称已经完成可靠学情诊断。

### 3.4 科研证据

**入口：** `RESEARCH_01_ACADEMIC_SEARCH_V1`
**路由：** 正确
**外部检索状态：** `deferred/not_initialized`

后台健康信息显示外部检索服务配置存在，但实际 Provider 尚未初始化，无法证明真实检索、筛选、DOI/arXiv 保留和引用核验链路已经可用。

**结论：** 当前是科研检索接口和流程，不是已完成真实证据验收的科研 Agent。

### 3.5 知识治理

**入口：** `LEARN_01_LOCAL_RETRIEVAL_V1`
**问题类型：** 能力错配

知识治理按钮没有独立的资产治理 Agent，而是复用了学习/知识问答 Agent。

因此它容易产生：

- “没有找到资料”；
- “请补充资产元数据”；
- 普通知识问答式总结；

而不是稳定完成：

- 资产版本核对；
- 来源和审批状态核对；
- 版本冲突识别；
- 发布阻塞项归类；
- 发布后和回滚检查清单。

**结论：** 该案例的根本问题不是提示词，而是路由到的能力不匹配。

### 3.6 学科求解

**入口：** `ACADEMIC_PROBLEM_SOLVER`
**路由：** 正确
**确定性工具：** 部分可用

专业求解内核已有 CoursePack、公式工具和验证规则，但仍存在：

- 多个工具未启用；
- 部分课程包只有 `basic` 或 `skeleton` 状态；
- 真实 Provider 与工作台任务链路未统一；
- 发布证据不足。

**结论：** 专业求解内核相对完整，但系统级真实执行链路仍未闭合。

## 4. 已确认的高优先级问题

### P0-1：后台 Provider 与模型健康状态不一致

后台 `/api/v1/health` 报告：

- `environment=production`；
- `requested_provider=mock`；
- `active_provider=mock`；
- `provider_mode=mock`。

但 `/api/v1/models/health?live=true` 显示 Qwen 可用。

这意味着“模型可用”不等于“工作台会使用该模型”。这会导致开发者看到真实模型健康，用户却收到 Mock 或本地降级结果。

同时，仓库 `.env` 是 development 配置，运行进程表现为 production，存在启动配置漂移。

### P0-2：结构化输出截断未被正确治理

当前问题包括：

- Schema 输出预算和业务复杂度不匹配；
- `finish_reason` 没有进入结构化错误详情；
- `StructuredOutputError` 没有针对截断自动重试；
- 前端只看到笼统的“执行失败”；
- 失败结果中课程资料数可能显示为 0，用户无法知道是模型输出失败还是检索失败。

真实评测报告：

- [备课模型评测](/C:/Users/86184/Desktop/xinzhi-daoxue/local_storage/evaluations/model_agents_20260821T113608Z.json)；
- [作业诊断模型评测](/C:/Users/86184/Desktop/xinzhi-daoxue/local_storage/evaluations/model_agents_20260821T113618Z.json)。

### P0-3：RAG 降级时仍可能进入需要资料依据的业务

当前 embedding 和 reranker 未加载，但系统仍暴露课程问答、备课、学习路径和知识治理能力。

向量数量正常不代表检索质量正常。若没有明确质量门禁，模型可能：

- 使用不相关资料；
- 把 lexical fallback 当作语义检索；
- 在资料不足时生成看似完整的答案；
- 让用户误以为答案已经完成课程资料核验。

### P0-4：发布预检与运行接口存在状态漂移

源码中的发布预检会根据 `publication_status` 阻止未发布 Agent 进入 production-ready，但当前运行 API 的场景就绪接口曾返回 production-ready=true，同时附带 `agent_publication_status:local` 警告。

这说明后台进程可能没有加载当前源码或当前配置，启动时缺少构建版本和配置快照校验。

## 5. 已确认的中优先级问题

### P1-1：Runtime 与 Legacy 执行分支并存

代码中仍存在：

- `legacy-runtime:*` 计划；
- `legacy_provider` 分支；
- `_build_legacy_plan()`；
- Router 中由旧规则继续主导的逻辑。

这与文档中“所有 Agent 统一通过 durable Runtime、没有 Legacy 执行分支”的表述不完全一致。

当前实际形态是 Runtime 外壳兼容旧业务执行器，而不是单一执行控制面。

### P1-2：展示测试只证明路由，不证明业务完成

`test_showcase_case_matrix.py` 主要检查：

- 六个按钮存在；
- Prompt 能路由到预期 Agent；
- response-depth 元数据存在。

它没有验证：

- 真实 Provider；
- RAG 命中内容；
- 结构化字段质量；
- 引用真实性；
- 发布边界；
- 失败恢复。

### P1-3：知识治理缺少独立能力边界

资产治理不应只是知识问答的一个 Prompt 变体。它至少需要独立的：

- 资产记录 Schema；
- 版本比较器；
- 审批状态模型；
- 权限状态模型；
- 发布阻塞规则；
- 回滚检查协议。

当前这些职责没有形成真正独立的 Agent/Runtime 能力。

### P1-4：科研检索的外部 Provider 没有完成真实初始化

配置存在不代表服务已可用。当前外部 Provider 多数为 `not_initialized` 或 deferred，无法支撑“科研证据”这一产品承诺。

### P1-5：游客模式的页面承诺与后台配置不一致

工作台页面展示“可以游客模式进入”，但实际点击后提示：

> 当前环境不允许游客模式。

浏览器页面加载正常、无明显控制台错误，但未登录用户无法完成真实任务提交验收。

### P1-6：多学科能力的注册状态高于实际实现状态

能力列表中存在多个课程和工具，但实际课程包为 `basic` 或 `skeleton`，部分工具关闭。注册表的“存在”不能直接解释为“可用”。

## 6. Agent 基础架构差距

### 已具备

- Agent 注册表；
- 集中式 Router；
- 结构化输入输出；
- durable Runtime；
- 节点状态和 SSE；
- 工具注册表；
- 基础回退策略；
- 部分可观测性。

### 与主流 Agent Runtime 的差距

1. **缺少稳定的通用执行循环**：尚未形成统一的 `Plan → Act → Observe → Replan`。
2. **Planner、业务服务和 Legacy 分支职责重叠**：同一请求可能在不同层被重新解释。
3. **工具调用协议不统一**：工具虽有注册信息，但权限、输入 Schema、观测结果和失败恢复没有完全统一。
4. **记忆和学习闭环不成熟**：学习建议主要是未校准启发式，不足以作为能力认定。
5. **能力真值分散**：Provider、Runtime、RAG、发布和证据状态由不同接口分别判断。
6. **真实评测没有接入发布门禁**：评测报告和生产发布仍是两套流程。
7. **领域能力边界不清晰**：知识治理复用学习 Agent，造成输出质量错位。
8. **模块职责过重**：关键文件过大，路由、模型、证据、业务和兼容逻辑相互耦合。

关键大文件包括：

- `apps/api/app/agents/router.py`：约 2257 行；
- `apps/api/app/services/academic_solver_service.py`：约 2028 行；
- `apps/api/app/services/internal_agent_execution.py`：约 1463 行；
- `apps/api/app/services/course_asset_review.py`：约 1305 行；
- `apps/api/app/services/learning_loop.py`：约 1213 行。

## 7. 尚未证明、不能直接下结论的事项

以下内容目前不能宣称成功，也不能仅凭现有测试判定失败：

- 六个案例在真实 Qwen 下的完整语义质量；
- 课程资料引用是否逐条正确；
- 科研检索的 DOI/arXiv 真实性；
- 学科求解在真实图片输入下的稳定性；
- 真实用户连续追问时的记忆一致性；
- Runtime 跨进程恢复和生产部署行为；
- RAG 热路径在模型加载完成后的真实召回质量。

这些事项需要真实 Provider、有效 RAG、认证用户和完整的端到端验收环境，不能用当前 Mock 或契约测试替代。

---

## 8. 审计结论

当前项目不是“功能完全失效”，而是处于以下状态：

- 路由层：基本可用；
- Runtime 合同层：基本可用；
- 真实模型层：部分可用，但预算和恢复不足；
- RAG 层：降级可运行，不能稳定支撑资料核验；
- 领域 Agent 层：存在能力错配；
- 发布层：未达到生产门槛；
- 前端层：静态页面可用，真实任务链路受认证和 Provider 配置影响；
- 架构层：具备雏形，但仍是双控制面和多层兼容架构。

因此当前最重要的问题不是继续增加 Agent 或界面功能，而是先解决：

1. 运行配置和能力状态统一；
2. 结构化输出截断与错误恢复；
3. RAG 质量门禁；
4. 知识治理能力错配；
5. Runtime/Legacy 单一执行边界；
6. 真实六案例验收和发布证据闭环。
