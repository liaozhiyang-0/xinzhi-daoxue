# 芯智导学：浏览器真实体验与回答质量专项加固

## 阶段定位

当前系统的主要问题已经不再是：

> “任务能不能跑起来”

而是：

> **“用户在浏览器里最终能不能稳定得到一份真正有用、完整、自然、可信的回答。”**

人工复测已经暴露出：

1. 解题流程经常降级，最终不给答案；
2. 不必要地进入人工审批；
3. 同一个问题重复提交，结果不稳定；
4. 后端测试大量通过，但浏览器真实体验仍然差；
5. `completed`、`waiting_review`、fallback 等技术状态不能代表用户真正拿到了可用答案；
6. 现有 Validator / Review / Degrade Policy 可能过度保守；
7. 用户自由问答与专业解题的最终回答质量需要重新验收。

因此本阶段必须从：

> Backend-Centric Testing

切换到：

> **Browser-Centric Product Acceptance**

---

# 最高原则

## 1. 浏览器最终结果是最高验收对象

任何修复都必须在：

```text
http://127.0.0.1:8000/workspace
```

真实提交并观察。

禁止仅凭：

```text
pytest passed
task completed
API 200
runtime finished
```

宣布问题修复。

---

## 2. 对普通学生问题，默认应该尽量直接回答

除非确实涉及：

- 必须教师审核的正式评分；
- 发布/治理权限；
- 高风险不可逆操作；

否则不要轻易：

```text
waiting_review
```

尤其：

- 电路解题；
- 数模电问题；
- 信号与系统；
- 普通知识问答；
- 学习解释；
- 学生追问；
- 图像题理解；

原则上应优先直接给出答案。

---

## 3. “降级”不能等于“不给答案”

如果模型、RAG、图片理解或外部工具能力不足：

系统仍应优先提供：

```text
当前可确认的信息
+
明确假设
+
可执行解法
+
结果或参数化结果
+
不确定性说明
```

而不是：

```text
无法完成
需要审核
建议补充信息
```

除非确实无法继续。

---

## 4. 同题稳定性必须提高

同一个问题重复提交时：

允许措辞不同，

但不允许频繁出现：

```text
一次给答案
一次降级
一次 waiting_review
一次答错
一次不回答
```

必须重点排查：

- Router 漂移；
- Agent 选择漂移；
- Provider fallback 漂移；
- RAG 随机性；
- Validator 阈值漂移；
- Review Policy 漂移；
- Prompt / Context 注入差异；
- 多模态预处理差异；
- 超时造成随机降级。

---

# 本阶段核心目标

## Q1 回答完整性

正常问题必须尽量有：

```text
直接结论
关键推导
最终答案
必要解释
```

## Q2 降级策略

降级后仍然要：

> 有结果，而不是只返回边界说明。

## Q3 审批策略

减少不必要 `waiting_review`。

## Q4 同题稳定性

同一道题多次提交，核心结论稳定。

## Q5 浏览器 E2E

所有关键修复都必须真实浏览器复测。

## Q6 真实用户问题

优先使用现有真实题目、电路图和人工发现的问题。

---

# 阶段停止条件

只有当以下条件满足，才允许收口：

- 普通解题任务不再频繁进入 waiting_review；
- 普通解题任务不再因为轻微不确定性直接不给答案；
- 同题重复 5 次核心结论基本一致；
- 浏览器中无 completed 但答案空洞；
- 浏览器中无“后端成功、前端用户拿不到结果”；
- 多图题至少能给出明确处理结果；
- 用户补充/纠正后系统能继续完成；
- 六个业务案例浏览器真实使用体验合格；
- Git commit 完成。
